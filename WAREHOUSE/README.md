## 1. Назначение системы

Мелкий оптово-розничный склад мебели (300–800 SKU, 2–4 кладовщика) ведётся в Excel и на бумаге: нет точных остатков, товар ищут «на глаз», инвентаризация занимает дни. ИС решает эти задачи:

- **учёт номенклатуры** — карточки товаров с габаритами, весом, хрупкостью и штрихкодом;
- **адресное хранение** — каждая единица товара привязана к ячейке `Стеллаж-Секция-Ярус`;
- **приёмку** — накладная поставщика → печать этикеток → автоматическое размещение по ячейкам;
- **сборку заказов** — резервирование и оптимальный маршрутный лист обхода склада;
- **инвентаризацию** — быстрая сверка факта с учётом и проведение расхождений;
- **контроль** — журнал «кто, когда, что изменил», отчёты, минимальные остатки.

## 2. Технологический стек

| Слой | Технология | Почему выбрано |
|---|---|---|
| Backend | Node.js 22–24, Express 4 | единый язык с фронтом, минимум конфигурации |
| Аутентификация | JWT (`jsonwebtoken`), пароли — `bcryptjs` | stateless-сессии на 12 часов, стойкий хеш паролей |
| БД | SQLite (встроенный модуль `node:sqlite`) | не требует установки сервера, нулевой порог запуска; схема переносима на PostgreSQL/MySQL |
| Frontend | React 18, Vite 5, React Router 6 | быстрая сборка, компонентная структура |
| Графики | Recharts | дашборд: занятость зон, остатки по категориям |
| Штрихкоды | JsBarcode (генерация CODE128), html5-qrcode (скан камерой) | этикетки и сканирование без покупки ТСД |

Архитектура — **монолит** (как в диаграмме `SystemArchitecture_Zmagazinovich.drawio`):

```
[Браузер / телефон: React SPA]
        │  HTTP + JSON (Bearer JWT)
        ▼
[Express: маршруты API + RBAC + бизнес-логика]
        │  SQL (node:sqlite)
        ▼
[SQLite: warehouse.db — справочники, остатки, документы, журнал]
```

В dev-режиме фронтенд поднимается отдельно (Vite, :5173, проксирует `/api` на сервер); в «продакшн»-режиме сервер сам отдаёт собранную папку `client/dist` — один процесс на :3001.

2. Откройте терминал VS Code: меню **Терминал → Создать новый терминал** или сочетание `Ctrl + ~` (тида). Убедитесь, что в панели терминала текущая папка — корень проекта (в приглашении видно `...\WAREHOUSE>`).

## 4. Как устроена работа (типовые сценарии)

### 4.1. Приёмка товара

1. Кладовщик создаёт **приёмку**: поставщик + позиции (поиск товара по названию/артикулу). Статус `Новая` — документ можно редактировать.
2. **«Подтвердить приёмку»** — товар зачисляется на остаток во временную ячейку зоны приёмки (`ПРИ-000`). Статус `Ждёт размещения`. Печатается лист **этикеток со штрихкодами** (CODE128) для оклейки товара.
3. **«Разместить по ячейкам»** — алгоритм автоматически подбирает ячейки хранения (см. п. 5.1), переносит туда остатки, отмечает позиции размещёнными. Статус `Размещена`.

### 4.2. Заказ и сборка

1. Менеджер создаёт **заказ**: покупатель + позиции. Система проверяет *свободные* остатки (`остаток − резерв`) и **резервирует** товар в конкретных ячейках. Нехватка → отказ с перечнем дефицита.
2. Кладовщик нажимает **«Начать сборку»** — строится **маршрутный лист**: строки «ячейка → товар → сколько взять», упорядоченные по обходу склада (см. п. 5.2).
3. По каждой позиции — **«Собрать»** (или сканирование штрихкода камерой): резерв списывается, остаток в ячейке уменьшается.
4. **«Отгрузить»** переводит заказ в `Отгружен`. Частичная отгрузка — с освобождением нереализованного резерва. Отмена заказа снимает резерв.

### 4.3. Инвентаризация

1. **«Начать инвентаризацию»** — по зоне или всему складу фиксируются ожидаемые количества по каждой паре «товар в ячейке».
2. Кладовщик обходит ячейки и вводит факт (или сканирует штрихкод). Расхождения подсвечиваются красным.
3. **«Закрыть и провести»** — учётные остатки корректируются по факту, формируется отчёт расхождений.

### 4.4. Прочие разделы

- **Карта склада** — 2D-схема зон: стеллажи колонками, ячейки квадратиками; цвет = заполнение (зелёный — свободо, жёлтый/оранжевый/красный — заняты), клик — состав ячейки, вместимость, статус.
- **Товары** — карточка с габаритами, объёмом, весом, классом ходкости A/B/C, минимальным остатком; где лежит (по ячейкам); этикетка со штрихкодом.
- **Зоны и ячейки** — CRUD зон/ячеек, генерация целого стеллажа «секции × ярусы» за один клик, ручная смена статуса (блокировка, обслуживание).
- **Остатки** — склад с фильтрами, ручной **перенос** товара между ячейками с автоподбором (проверка объёма, веса, габаритов).
- **Отчёты** — 5 отчётов + экспорт в CSV; **Журнал операций** — фильтры по сотруднику/действию/объекту/датам; **Дашборд** — KPI, графики, дефицит, последние операции; **Пользователи** — CRUD, роли, включение/отключение, смена пароля.

## 5. Ключевые алгоритмы

### 5.1. Размещение товара по ячейкам (`server/src/util.js → suggestCells`)

Кандидаты ранжируются в порядке приоритета:

1. **Докладка** в ячейку, где этот товар уже лежит (если хватает грузоподъёмности и объёма).
2. **Свободные ячейки «своей» ABC-зоны** (класс ходкости ячейки = классу товара):
   - хрупкие товары — только нижние ярусы (`level ≤ 2`);
   - сортировка: сначала нижние ярусы, затем — близость к зоне отгрузки (координаты зон);
   - проверка: габариты проходят в ячейку (с учётом поворота), объём партии ≤ свободного объёма, вес ≤ грузоподъёмности.
3. Если ячеек «своего» класса не хватило — свободные ячейки **вне зоны класса**, подходящие по габаритам (с пометкой в отчёте).

Не размещённый остаток остаётся в зоне приёмки; повторное размещение дозаполняет его после освобождения ячеек.

### 5.2. Маршрут сборки

Позиции заказа раскладываются по ячейкам с резервом и сортируются: `координата Y зоны → координата X зоны → стеллаж → секция → ярус`. Получается непрерывный обход склада без возвратов.

### 5.3. Резервирование

Резерв «прилипает» к конкретным строкам остатка (FIFO по id ячейки). Операции: создание заказа (+= резерв), сборка (−), отмена/частичная отгрузка (снятие). Перемещение заблокированного резервом товара запрещено.

## 6. Модель данных

Схема БД (`server/src/db.js`) точно соответствует **ER-диаграмме** из `diagrams/`:

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `roles` | 4 роли (admin/manager/warehouse/loader) | `code`, `name` |
| `permissions` | атомарные права (`products.edit`, `receipts.place`, …) | `code` |
| `role_permissions` | матрица доступов из ТЗ | FK |
| `users` | учётные записи | `login`, `password_hash`, `role_id`, `is_active` |
| `categories` | иерархия номенклатуры (родитель → подраздел) | `parent_id` |
| `products` | товар | `sku`, `barcode` (EAN-13), габариты мм, вес кг, `turnover_class` A/B/C, `is_fragile`, `min_stock` |
| `zones` | зоны склада | `type` storage/receiving/shipping, координаты для карты и расчёта близости |
| `cells` | ячейки хранения | `code` (Адрес), FK `zone_id`, стеллаж/секция/ярус, габариты, `max_weight_kg`, `max_volume_m3`, `turnover_class`, `status` |
| `stock` | остаток «товар в ячейке» | `quantity`, `reserved`, UNIQUE(product, cell) |
| `receipts` / `receipt_items` | приёмка и позиции | `number`, `supplier`, `status`, `placed` |
| `orders` / `order_items` | заказ и позиции | `number`, `customer_name`, `status`, `picked` |
| `inventories` / `inventory_items` | инвентаризация и строки сверки | `expected_qty`, `fact_qty` |
| `operation_logs` | журнал | `user_id`, `action`, `entity`, `entity_id`, `details` (JSON), `timestamp` |

**Жизненные циклы** (соответствуют диаграммам состояний):

```
Приёмка:  Новая → Подтверждена → Размещена   (отмена: Новая/Подтверждена → Отменена)
Заказ:    Новый → Сборка → Отгружен           (отмена: Новый/Сборка → Отменён)
Ячейка:   Свободна ↔ Занята;  Заблокирована / Обслуживание — ручные статусы
Инвентаризация: Открыта → Закрыта
```

## 7. REST API

Все методы — под `/api`, кроме `POST /api/auth/login` и `GET /api/health`, требуют заголовок `Authorization: Bearer <token>`. Ответы ошибок — `{"error": "текст на русском"}` с кодом 400/401/403/404/409.

| Группа | Эндпоинты |
|---|---|
| Сессия | `POST /auth/login` · `GET /auth/me` · `PUT /auth/password` |
| Пользователи | `GET /users` · `POST /users` · `PUT /users/:id` · `DELETE /users/:id` · `GET /roles` |
| Категории | `GET/POST /categories` · `PUT/DELETE /categories/:id` |
| Товары | `GET /products?q&categoryId&turnover` · `GET /products/:id` · `GET /products/barcode/:code` · `POST/PUT/DELETE /products[/:id]` |
| Зоны/ячейки | `GET/POST/PUT/DELETE /zones[/:id]` · `GET /cells?zoneId&status&q` · `GET /cells/map` · `GET /cells/suggest` · `GET /cells/:id/contents` · `POST /cells` · `POST /cells/bulk` · `PUT/DELETE /cells/:id` |
| Остатки | `GET /stock?productId&cellId&zoneId&q` · `POST /stock/move` |
| Приёмки | `GET /receipts` · `GET /receipts/:id` · `POST /receipts` · `PUT /receipts/:id` · `POST /receipts/:id/confirm` · `/place` · `/cancel` |

## 9. Безопасность

- Пароли — только bcrypt-хеш (10 раундов), никогда не возвращаются клиенту.
- JWT (12 ч, случайный секрет в `data/.jwt-secret`); неактивная учётная запись отклоняется на уровне middleware.
- **RBAC на двух уровнях**: серверная проверка права на каждый эндпоинт (`perm('receipts.place')` и т.д.) + скрытие пунктов меню/кнопок на клиенте.
- Защита данных: нельзя удалить товар с остатками, ячейку с товаром, зону с ячейками; нельзя отключить/удалить себя; отмена приёмки возвращает товар из зоны приёмки.
- Все изменяющие операции пишутся в `operation_logs` (кто, когда, что, детали в JSON).
